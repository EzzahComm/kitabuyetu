**All four gated route groups implement their guard as a client-side `useEffect` redirect, not a server-render check.** Every guard's own code comment cross-references a server-side enforcement point it claims to mirror (`proxy.ts` for JWT audience/role, or a named `assert*()` function) — Pass 0 records the claim; whether the server side actually enforces the same rule for every route under it is unverified here and is explicitly H7's subject in Pass 1.

### The actual server-side enforcement point: `proxy.ts`

`proxy.ts:332` — `matcher: ['/api/:path*']`. This is Next.js edge middleware, runs before every `/api/*` request (not before page renders — pages get their data guard transitively, by their API calls 401ing).

- Verifies a `jose`-signed JWT (`proxy.ts:2`).
- Two token shapes share one verification path (`proxy.ts:54-75`): tenant tokens carry `groupId`+`role`; backoffice tokens carry `platformRole`.
- Sets `x-group-id`, `x-role` / `x-platform-role` request headers (`proxy.ts:259,316-324`) that downstream route handlers and `withPermission`/`withRole`/`withPlatformRole` wrappers read.
- Explicit unauthenticated carve-outs (`proxy.ts:112-119,160-161,205-206,286-287`): M-Pesa/Daraja callback paths, generic/email webhook paths, `PUBLIC_AUTH_PATHS`, `/api/v1/jurisdictions/*`, and the two auth-verify start/complete endpoints.
- A documented cross-audience carve-out (`proxy.ts:145-154,300-311`): `/api/v1/organization/*` accepts a **backoffice-audience** token reshaped to look tenant-shaped, because the enterprise portal calls tenant-prefixed API paths but authenticates as backoffice. Recorded as a fact; whether this creates a scoping gap is Pass 1/H3 territory (funding/organization scoping).

## 3. Schema inventory

Source: live Supabase introspection (`pg_class`/`pg_policy`/`information_schema`), project `qztcgryhoanennsizcll`, queried directly — not read from migration files, so this reflects what's actually deployed, not what the migration history intends.

- **130 tables** in `public` schema.
- **357 foreign-key constraints** (`information_schema.table_constraints`).
- **RLS enabled: 129 of 130 tables.** The one exception: **`public.invoice_sequences` — `rls_enabled: false`.** Supabase's own advisory tool flagged this as `critical` and its output text instructs that it be surfaced directly rather than deferred: *"These tables are fully exposed to the anon and authenticated roles used by Supabase client libraries — anyone with the anon key can read or modify every row."* Recorded here as inventory; whether it's exploitable in practice (this app doesn't appear to route through PostgREST/anon key for tenant data — see §5) is Pass 1/H8's job, not Pass 0's, but it is flagged in the checkpoint summary below because the tool that surfaced it requires that.
- **RLS forced (`relforcerowsecurity`): 84 of 130 tables** — the other 45 RLS-enabled-but-not-forced tables' policies don't apply to the table owner. Whether the table owner (i.e., the `postgres` role used by `withAdminDb`) is a meaningful bypass path for any of those 45 is not evaluated in Pass 0.
- Policy counts per table are in the query result cached at tool-call time (not persisted as a TSV — the raw SQL is reproducible: `SELECT c.relname, c.relrowsecurity, c.relforcerowsecurity, count(p.*) FROM pg_class c JOIN pg_namespace n ON n.oid=c.relnamespace LEFT JOIN pg_policy p ON p.polrelid=c.oid WHERE n.nspname='public' AND c.relkind='r' GROUP BY 1,2,3`). Most tables carry 1, 3, or 4 policies; a handful of high-value financial tables (`payments`, `invoices`, `bill_manager_invoices`) show exactly 1 policy each — worth a closer read in Pass 1, not asserted as a gap here.

## 5. Client entry points — direct Supabase vs via server

**No client component calls Supabase directly.** Evidence:

- `lib/supabase/client.ts` (`createBrowserClient` from `@supabase/ssr`) — grepped across the entire repo (`*.tsx`, `*.ts`): the **only** references to it outside itself are inside pre-existing audit markdown (`docs/capital-layer/impact-report.md`, `docs/audits/PRODUCTION_SCHEMA_DRIFT_AUDIT.md`, and the older top-level `audit/*.md` set — see §6). **Zero application code imports it.** It is dead code.
- `lib/supabase/server.ts` (`createClient`/`createAdminClient`, both `createServerClient` from `@supabase/ssr`) — same result: zero call sites outside its own file.
- Every client-side data fetch instead goes through `configureApiClient()` (`lib/api/client.ts`, wired up in all four gated layouts — `app/(dashboard)/layout.tsx:23`, `(admin)/layout.tsx:39`, `(enterprise)` uses it transitively via the same hook layer, `(member)/layout.tsx:32`) hitting the Next.js `/api/v1/*` and `/api/admin/*` route handlers over `fetch`. 15 files were confirmed calling this client layer directly (hooks + a handful of components) in a bounded grep sample; the pattern is repo-wide by construction (`lib/api/endpoints.ts` centralizes the per-feature fetch wrappers other hooks call).

**The actual privilege/bypass boundary is not Supabase's service-role key — it's a second Postgres role.** `lib/db/index.ts`:
- `withDb(ctx, fn)` (`:127-144`) — connects via `tenantPool`, opens an explicit transaction, and runs `SELECT set_config('app.current_user_id'/'app.current_group_id'/'app.current_role'/'app.current_organization_id', …, TRUE)` (`:111-121`) before the caller's query — this is what makes RLS policies (which read those same `app.current_*` settings, per ADR-001) apply per-request.
- `withAdminDb(fn)` (`:162-177`) — connects via the plain `pool` (the `postgres` role in production, per `docs/adr/001-bypassrls-two-role-split.md`, which carries `BYPASSRLS`), no tenant context set at all.
- **309 call sites across 91 files** use `withAdminDb(` (grep count, repo-wide). ADR-001 (`docs/adr/001-bypassrls-two-role-split.md:174-183`) already documents this as a known, intentional, *unfinished* migration: Phases 0-1 (the tenant/`app_tenant` split itself) are live in production since 2026-08-05; "Phase 3" — moving ~130 of these `withAdminDb` call sites (its own estimate) that don't structurally need admin privilege onto `withDb` — is explicitly recorded there as deferred, not done. Pass 0 records the count as of now (309/91); reconciling it against ADR-001's own estimate is Pass 1/H8 material.
- `TENANT_DATABASE_URL` (`lib/db/index.ts:91-95`) is optional — if unset, `tenantPool` **silently falls back to the same pool/role as `withAdminDb()`**, per the code's own comment: *"a no-op until that role exists."* Whether this fallback is actually engaged in the current production environment is unverified in Pass 0 (would need the live env var, not source) — flagged for Pass 1/H8's exact-verification-step list.
