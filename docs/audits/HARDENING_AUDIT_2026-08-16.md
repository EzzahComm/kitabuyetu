# Hardening audit — 2026-08-16

Codebase-wide pass following the loan interest correction (migration 148), the
repayment-cadence work (149) and disbursement payment-method labelling (150).

**Method.** Every finding below was reproduced against the production database
inside a rolled-back transaction, not inferred from reading code. Claims about
live state come from querying it. Nothing was written except the three
migrations already merged.

**Headline:** the loan CSV importer is broken end to end — three separate
defects in one code path. It has never been exercised in production, so there
is **no data damage**: the only loans that exist are the four THE FIONA'S loans,
all with correct schedules and full funding attribution. This is a latent
failure, not an incident.

---

## Finding 1 — CSV loan import fails at COMMIT, always

**Severity: high (feature is entirely non-functional).**
`lib/services/import.service.ts:1027`

The importer inserts loans with no `loan_funding_splits` row. The constraint
trigger `trg_assert_loan_attribution_on_status` calls
`private.assert_loan_funding_splits_balance`, which covers:

```sql
IF v_status IS NULL
   OR v_status NOT IN ('disbursed','active','completed','defaulted','written_off')
THEN RETURN;
```

`LoanCsvRowSchema` allows exactly `active | completed | defaulted | written_off`
and defaults to `active` — **all four are inside that set**. So every imported
loan row violates the check.

Reproduced verbatim against production:

```
inserted loan a9895878-… status=active (per-row INSERT succeeded)
Deferred check FAILED at commit-time:
  loan_funding_splits for loan a9895878-… sum to 0.00 but the principal
  is 130000.00 — every disbursed loan must be fully attributed to its
  funding sources
```

**Why the per-row error handling cannot save it.** The trigger is
`DEFERRABLE INITIALLY DEFERRED`, so it fires at **COMMIT** — after the import
loop has finished. `import.service.ts` wraps each row in `try/catch` and
accumulates `errors[]`, but that catch is long out of scope by then. The whole
transaction aborts and the user gets an opaque failure rather than the row-level
diagnostics the importer was built to give.

**Fix direction.** Historical imported loans *were* funded from the group's own
savings, so attribute them to the auto-provisioned `internal_savings` source in
the same statement as the loan insert (a data-modifying CTE — two separate
statements will not work if the caller is ever changed to commit per row).

## Finding 2 — imported loans get no repayment schedule, so no reminders

**Severity: high.** Same code path.

Schedules are generated by a trigger, not by the service:

```sql
CREATE TRIGGER trg_loans_generate_schedule AFTER UPDATE ON public.loans …
-- private.trg_loan_on_disburse():
IF NEW.status = 'disbursed' AND OLD.status IS DISTINCT FROM 'disbursed' THEN
  PERFORM public.generate_loan_schedule(NEW.id);
```

It is **AFTER UPDATE only**, and additionally requires a transition *into*
`disbursed`. The importer does a single `INSERT` at status `active`, so the
trigger never fires. Confirmed in the reproduction: `schedule rows generated: 0`.

Consequences, in order of how much they matter:

1. **No reminders.** `handleLoanDueAlerts` selects from `loan_repayments`. No
   rows means an imported borrower is never reminded of anything, silently.
2. No instalments, no due dates, no `next_payment_date`.
3. Repayment allocation has nothing to allocate against.

Note this interacts with the cadence work: `generate_loan_schedule` now honours
`repayment_frequency`, so fixing this correctly means imported loans can also be
weekly. The importer has no column for it — defaulting to `monthly` is right.

## Finding 3 — the importer computes interest with its own, now-wrong, formula

**Severity: high (silent financial misstatement).**
`lib/services/import.service.ts:1195`

```ts
function computeTotalRepayable(principal: number, annualRatePct: number, termMonths: number): number {
  const monthlyRate = annualRatePct / 100 / 12;      // <-- treats the rate as ANNUAL
  const totalInterest = principal * monthlyRate * termMonths;
```

This is a **second implementation** of the interest formula, in TypeScript,
duplicating what `generate_loan_schedule` does in SQL. Migration 148 established
that `loans.interest_rate` is a **monthly** rate; this function still divides by
12, and its parameter is even named `annualRatePct`.

Measured on the same inputs as the live Reuben loan (130,000 @ 10.00 × 12):

| Path | Interest | Total repayable |
|---|---:|---:|
| `generate_loan_schedule` (flat, post-148) | 156,000 | **286,000** |
| `computeTotalRepayable` (importer) | 13,000 | **143,000** |

**Interest understated 12×; total repayable understated 2×.** A group importing
its loan book would see every balance at half its true value, with no error.

**Fix direction.** Delete the function. `generate_loan_schedule` already writes
`total_repayable` and `outstanding_balance` itself, so once Finding 2 is fixed
the importer should not compute these at all — it should let the schedule
generator be the single source of truth. Two implementations of one financial
formula is what created this divergence, and re-deriving the formula in TS would
just reset the clock on the next drift.

## Also worth a decision (not defects)

- **Weekly reminder overlap.** `handleLoanDueAlerts` stages on day offsets
  (3 before / due / overdue 3, 7, 14). At weekly cadence the `overdue_7_days`
  and `overdue_14_days` stages for one instalment fire while the next two are
  already due. Noisy but not wrong; the stages were designed for monthly spacing.
- **Month-end due-date drift.** Due dates accumulate from the previous due date,
  so a loan disbursed on the 31st clamps to 28 Feb and then stays on the 28th
  forever. Pre-existing, pinned by test, unchanged. Only affects loans disbursed
  on the 29th–31st; weekly cadence is immune (`INTERVAL '1 week'` is pure day
  arithmetic and is unaffected by month length or leap years).
- **Maker-checker does not test disinterest.** `approveDisbursement` rejects only
  `created_by === ctx.userId`. On the live EZZAHCOMM disbursement the sole
  eligible approver is also a borrower of the capital being approved.
- **`installmentCount()` in `loan.schema.ts` mirrors the SQL formula** for UI
  preview. Intentional duplication, documented at both sites, but it is the same
  shape of risk as Finding 3 — if the SQL formula changes, this must too.
