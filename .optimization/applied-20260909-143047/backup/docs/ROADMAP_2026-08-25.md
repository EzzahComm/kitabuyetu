## Engineering constraints (apply to every item)

### 1. Backward compatibility is non-negotiable

Live groups are transacting real money on this system today. Every change below must leave an existing group's behaviour **byte-identical unless that group opts in**.

Concretely, this means:

- **Schema changes are additive only.** New columns carry a `DEFAULT` that reproduces today's behaviour. No `DROP COLUMN`, no type changes, no renames on live tables. A migration that would rewrite an existing row's meaning gets a new column instead.
- **API contracts gain fields, never lose or retype them.** `/api/v1/*` responses may add keys; removing or changing a key's type is a new version. New request params are optional with today's behaviour as the default.
- **Feature flags and plan entitlements default to off/current**, so an un-migrated group is indistinguishable from today.
- **Migrations are not auto-deployed.** A green Vercel deploy never proves a migration is live in production — every schema item below needs the migration applied and confirmed separately, and the code must tolerate running *before* its migration lands.
- **`CREATE OR REPLACE FUNCTION` resets grants**, and a new `CREATE VIEW` is auto-granted to `anon`/`authenticated`. Both have punched holes in RLS in this repo before. Any DDL below must re-`REVOKE` explicitly and be followed by an advisor run.

### 2. Nothing ships that the product cannot back

Established by the hero audit. A screen or a marketing page may not state a capability the code does not have. Where the two disagree, the code is the source of truth and the copy changes.

## Thread 4 — Revenue

### 4.1 Per-group M-Pesa shortcodes (white-label plan)

The monetization play. Path B from the Changi$ha architecture — the one collection path that earns a fee without custody.

**The seam:** `resolveDarajaCredentials()` in `lib/services/daraja.service.ts`. Every call funnels through four module-scope constants at lines 56-60; replace them with a resolver and the rest is incremental.

**Scope cut that makes v1 cheap — STK Push only.** STK Push carries a `CallBackURL` *per request*, so callbacks route per group without touching `registerC2BUrls`. Direct-PayBill (C2B) and outbound B2C/B2B come later.

| Step | BC guarantee |
|---|---|
| `groups.collection_mode` (`pooled`\|`own_paybill`) | `DEFAULT 'pooled'` — every existing row unchanged |
| `group_daraja_credentials` table, encrypted via existing `ENCRYPTION_KEY` | New table; absent row ⇒ platform credentials |
| `resolveDarajaCredentials(groupId)` | Returns platform constants when no override exists ⇒ **identical behaviour for every group today** |
| Optional credentials param on `initiateStkPush` / `StkPushInput` | Optional; omitted ⇒ today's path |
| Per-group callback URL | Additive — the existing callback URL keeps resolving |
| `WHERE collection_mode = 'pooled'` in `accounting.service.ts:755-762` | Every existing group matches ⇒ reconciliation output byte-identical on day one |
| `ownPaybill` entitlement | Copies the existing `assertWhiteLabelAllowed` gate; defaults off |

**Ship date is set by procurement, not code.** A group needs its own paybill plus a Daraja app — Safaricom KYC you do not control. **Target groups that already hold a paybill** (SACCOs, larger chamas) and the launch cohort onboards the day the code lands.

**Caution:** if any part of the motivation is the custody exposure, this does not move it. The pooled majority stays exactly as custodial, and you would be running *mixed* custody — harder to reason about than one model. Be clear which goal is being bought.
