# 05 — Code Quality & Maintainability Findings

**Date:** 2026-07-27. The `no-explicit-any` item below was the subject of a full multi-session ratchet completed earlier this same day (see [[project-kitabu-yetu-audits]]) — re-verified as still clean rather than assumed.

## Swallowed errors

- ✅ **Zero genuinely-empty `catch` blocks found** (`catch (e) {}`-shaped, no logging, no rethrow, no explicit no-op justification) across `app`/`lib`.
- The pattern that *does* exist — `.catch(() => {})` on a handful of fire-and-forget calls (`revokeRefreshToken(...).catch(() => {})`, `storeRefreshToken(...).catch(() => {})` in the auth refresh/login/logout routes) — is a **deliberate best-effort pattern on genuinely non-critical side effects** (revoking an old token, storing a new one), not the "hides a real bug" anti-pattern the brief warns about from the registration-endpoint debugging history. Distinguishing this matters: flagging it as equivalent to a truly swallowed error would misdirect future cleanup effort at code that's actually fine.
- `data-import/page.tsx`'s one bare `catch {}` (discarding a preview) is a genuine "don't care if this fails, the row still shows as discarded either way" UI no-op — low-stakes, not a hidden bug risk.

## Structured error handling

- ✅ **156 of 167 routes** use the shared `handleError`/`ok`/`created` response helpers (`lib/utils/response.ts`) — a consistent envelope (`{success, data}` / `{success: false, error, code}`) across almost the entire API surface. The 11 that don't are the webhook receivers (WhatsApp, Resend, SendGrid, M-Pesa callbacks) and the two cron endpoints — all of which correctly return provider-contract-shaped or minimal-shaped JSON instead of the app's own envelope, since their callers are external systems, not the app's own `lib/api/client.ts`. Not a gap — the right call for each of those 11.

## TypeScript strictness (`no-explicit-any`)

- ✅ **Fully closed as of this session** (commit `c0c0b19`, earlier today) — every one of the original 227 usages was fixed by typing the real endpoint/DB shape (not just silencing with `unknown`), and `@typescript-eslint/no-explicit-any` is now a hard lint error in `eslint.config.mjs`, verified in CI. Re-grepped fresh for this audit pass: the only 4 remaining string matches are false positives (the English phrase "has any completed repayments" in a comment/UI string, and a code comment quoting old, already-fixed code for historical context) — confirmed by reading each match directly, not just trusting the count. No finding.
- Side effect worth recording here rather than only in the audit-log memory: fixing these 227 usages by typing the real wire/DB shape (instead of leaving them `unknown`) surfaced roughly 18 real, previously-silent production bugs (missing `pageSize` fields, wrong field names, a TanStack Query v5 API-shape mismatch, a member password-hash leak, an SMS Centre page that was completely non-functional in production) — see [[project-kitabu-yetu-production-incidents]] for the full list. This is direct evidence for why this specific code-quality item was worth prioritizing over some of the others in this report.

## Component structure / separation of concerns

- Sampled several `(dashboard)` pages during this session's own Phase D work (accounting, dividends, credit-scores, welfare, investments, meetings) — the established pattern is data-fetching via typed TanStack Query hooks (`hooks/use-*.ts`), presentation in the page component, business logic in `lib/services/*.ts`. Not perfectly uniform (e.g. `accounting/page.tsx` still inlines its new-journal-line editor logic directly in the page rather than a hook), but no case found where a page directly runs raw SQL or bypasses the service layer.

## Naming consistency

- Damm check-digit-validated ID formats (`KY#######` group codes, 14-char member codes) are generated by DB functions (`allocate_membership_no`, `damm_check_digit`) and validated the same way everywhere sampled — no drift found between, e.g., a route that accepts a looser format than what's actually issued.

## Duplicated logic (marketing vs. app)

- ✅ **N/A as stated** — there is no separate marketing-site codebase in this repo; the public landing page (`app/page.tsx`) and `/pricing` live in the same Next.js app as the authenticated product, so there's no cross-repo constant/type drift risk of the kind the brief describes. Not flagging as a gap since the premise doesn't apply.

## Logging at key business events

- Confirmed (from the accounting-audit series' own implementation, re-verified present not re-derived): audit-log writes exist on the three mutating `accounting.service.ts` functions, on manual-journal maker-checker actions, on fiscal-period close/reopen, on loan default/write-off, and on organization disbursement approve/reject. `logger.error`/`logger.warn` calls are used consistently at every webhook/cron failure point sampled in Phase 2.
- Did not verify a *complete* enumeration of "every key business event has a log line" (registration, share-out, meeting resolutions) — this would need a dedicated pass cross-referencing the Nexus logging standard mentioned in the brief against every mutating service function, which wasn't done exhaustively here given the size of the codebase (66 service files). **Recommend** as a follow-up if structured business-event logging (as opposed to error logging, which is solid) becomes a product priority.

## Test coverage on critical paths

- **42 test files** exist (`__tests__/unit` + `__tests__/integration`), up from 37 at the last audit. Critical-path coverage is meaningfully better than the brief's feared "near-zero": `contributions.test.ts`, `loans.test.ts`, `disbursements.test.ts`, `reallocations.test.ts`, `accounting.test.ts` (covers the shared journal-posting functions directly, including this session's own `postSystemJournal`/`postContributionJournal` fixes), plus three dedicated **tenant-isolation** test files (`mpesa-disbursements-tenant-isolation.test.ts`, `org-disbursements-tenant-isolation.test.ts`, `payment-requests-tenant-isolation.test.ts`) that run against a **real Postgres instance** in CI (not mocked) — this is a materially stronger test posture than the brief's checklist implies is typical for this class of app.
- **Genuine gap, specifically checked and confirmed**: no test file directly exercises the **registration** flow (`register_group()` / `POST /api/v1/auth/register`) end-to-end — it appears only as a test-fixture helper (`__tests__/integration/helpers/fixtures.ts`) used to set up state for *other* tests, never as the subject under test itself. Given registration is explicitly named in the brief and was also the subject of a real historical production incident (the module-scope-throw build failure, [[project-kitabu-yetu-production-incidents]]), this is worth closing specifically rather than assuming the fixture-helper usage counts as coverage.
- `jest --ci` is a required, blocking CI job (`OPTIMIZATION_CLEANUP_AUDIT.md` Critical #1, confirmed still wired into `.github/workflows/ci.yml` and observed passing on every commit pushed this session) — so whatever coverage exists is actually enforced, not just present-but-ignorable.
