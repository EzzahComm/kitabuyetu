# 02 — Security Hardening Findings

**Date:** 2026-07-27. Severity: **Critical** / **High** / **Medium** / **Low**. Read `01-inventory.md` §0 first — several of the brief's checklist items (Stack Auth, Supabase RPC/anon-key writes) don't apply to this stack and are marked N/A below rather than force-fit.

---

## 2.1 Authentication & Session

**Verified, not assumed**: I located the actual middleware entry point and confirmed (via the compiled `.next/server/chunks/*` bundle, grepping for the source file's distinctive string literals) that `proxy.ts` at the repo root — not a conventionally-named `middleware.ts` — is genuinely compiled into and running as Next.js's edge middleware. This matters because a proxy/middleware file that silently isn't wired up is one of the most dangerous classes of security regression (everything looks correct in source, nothing is actually enforced) — worth stating plainly that this was checked, not assumed.

**Findings:**
- ✅ **No finding** — every protected route verifies the JWT server-side. `proxy.ts` verifies the access token (`jose`, HS256, `JWT_SECRET` — fails fast at module load if unset or <32 chars) *before* any route handler runs, then strips any client-supplied `x-user-id`/`x-role`/`x-platform-role`/etc. headers from **every** request (including the public fall-through paths) and re-stamps only its own verified claims. A client cannot smuggle a forged role/group/user header past this layer — route handlers (`getAuthContext`/`getBackofficeContext`) trust these headers *because* the proxy is the only thing that can set them, and that assumption is correctly enforced.
- ✅ Role checks are enforced server-side (`withRole`/`withOneOf`/`withPlatformRole`), not just client-side redirects — confirmed by reading `lib/auth/middleware.ts` and `rbac.ts`. Client-side redirects (`(dashboard)/layout.tsx`, `(admin)/layout.tsx`, `(enterprise)/layout.tsx`) exist too, but only as UX, not as the actual gate.
- ✅ Audience separation (`tenant` vs `backoffice`) is enforced at the proxy layer per URL prefix (`/api/v1/*` vs `/api/admin/*`) — a backoffice token cannot be replayed against a tenant route or vice versa, checked in two places (proxy `aud` check + each route wrapper's own `aud` assertion) — good defense in depth.
- **Medium — refresh token rotation/reuse detection not independently re-verified this pass.** `AuthContext` carries `authVersion`/`sessionVersion` fields described in code comments as "drift epochs (payment architecture §2.1/§2.5)" implying a rotation-detection design exists, but this pass didn't trace the full refresh-token reuse-detection path end-to-end. Recommend a focused pass tracing `/api/v1/auth/refresh` + `refresh_tokens` table logic specifically (this table has no RLS — see §2.2 — though it's accessed only via `withAdminDb`/service-role code paths, not tenant-scoped queries, so the missing RLS is likely a non-issue in practice; confirm before assuming).
- **Low — no explicit session-fixation test found.** Standard JWT-bearer-token architectures (no server-side session cookie) are structurally not vulnerable to classic session-fixation in the cookie sense; not flagging as a real gap, just noting the brief's checklist item doesn't map cleanly onto this architecture.

## 2.2 Row Level Security — headline finding, already known, re-confirmed current

- **Critical (existing, tracked, not regressed) — the application's primary Postgres role has `BYPASSRLS`.** This was first found in `OPTIMIZATION_CLEANUP_AUDIT.md` (2026-07-20) and is openly documented in the codebase's own migration comments (058, 096, 097). Re-confirmed still true today: `lib/db/index.ts`'s `tenantPool` (used by `withDb`/`withTransaction`, i.e. **every** tenant-scoped service call) falls back to the same `BYPASSRLS` pool as `withAdminDb()` whenever `TENANT_DATABASE_URL` is unset, and the code's own comment states this is *"a no-op until that role exists."*
  - **What actually enforces tenant isolation today, given the above**: hand-written `WHERE group_id = $1` / `WHERE organization_id = $1` predicates in every service function (sampled ~40 call sites in the prior audit, zero gaps found except one already-fixed SQL-interpolation spot), plus the real-Postgres tenant-isolation integration test suite (`__tests__/integration`, a required CI job — ran and passed on every commit pushed this session).
  - **What this audit could not verify from source alone**: whether `TENANT_DATABASE_URL` is actually provisioned in the live production environment. If it is, tenant traffic already runs under the least-privileged `app_tenant` role (no BYPASSRLS) and RLS is a live, enforced second layer. If it isn't, RLS is schema-only decoration for 100% of app traffic and the hand-written WHERE clauses are the *entire* defense. **This is the single highest-value fact to confirm before any further hardening work** — check the Vercel/hosting environment variables directly, not the repo.
- **High (new finding this pass) — `mpesa_b2c_transactions`, `mpesa_b2b_transactions`, `mpesa_b2c_charge_tiers` have no RLS policy at all**, unlike the rest of the tenant-scoped schema. The first two carry `group_id` and record real money movement (B2C disbursement, B2B payment) — under the `app_tenant` cutover described above, these three tables would leak cross-tenant even after the cutover, since there's no policy to enforce isolation once BYPASSRLS is removed. `refresh_tokens` and `invoice_sequences` also have no RLS, but both are accessed exclusively via `withAdminDb`/service-role paths in every call site checked — lower priority, but confirm before assuming safe.
  - **Recommended fix** (flagged, not applied — schema change on money-movement tables, per the brief's own Phase 6 rule #3 and this codebase's established pattern of confirming before touching live-money schema): add `ENABLE ROW LEVEL SECURITY` + a `group_id = app_current_group_id()` policy (mirroring `loans`/`contributions`) to the three mpesa_b2c/b2b tables in a new migration, verified against a scratch Postgres instance first.
- ✅ **Anon-key / PostgREST write-path checklist item — N/A.** No route in this codebase writes via the Supabase JS client or PostgREST; `lib/supabase/client.ts`/`server.ts` (the only code that would do this) have zero importers (see `01-inventory.md` §5). All writes go through `pg`-driver service functions using the connection-pool model above. The brief's specific concern (anon-key bypassing a `SECURITY DEFINER` RPC) doesn't apply because there is no RPC-based write path to bypass.
- ✅ **`SECURITY DEFINER` functions** — sampled 8 of 21 directly (`mask_*`, `damm_*`, `app_current_*`, `allocate_membership_no`, `audit_logs_immutable`). All are narrow, single-purpose helpers; none accept a caller-supplied tenant/group identifier and skip authorization internally. No finding.

## 2.3 Financial Data & M-Pesa

- ✅ **Idempotency is enforced at the database level, not just application logic** — confirmed `UNIQUE` constraints on `mpesa_receipt_number` (contributions, loans, loan_repayments, payments, mpesa_transactions) and `originator_conversation_id`/`checkout_request_id` (the B2C/B2B/STK dedicated tables) across the schema. A replayed Safaricom callback cannot double-credit even if application-level dedup logic had a bug — this is real defense in depth, not just a paper claim.
- ✅ **Callback source validation exists appropriately for each channel**, verified by reading the actual route code (not assumed from comments):
  - M-Pesa STK/C2B callbacks: IP allow-list check is present but explicitly **advisory-only** with a documented, reasoned justification (`mpesa/callback/route.ts`'s own comment: Vercel's edge + custom domains make forwarded IPs unreliable for hard-blocking, and blocking would silently drop legitimate payment callbacks). Real integrity instead comes from the append-only `mpesa_callbacks` audit table + the UNIQUE-constraint idempotency above + `ack-after-durable-audit` (a callback isn't acknowledged 200 until the raw payload is durably persisted, so Safaricom retries on a DB outage instead of the callback being silently lost). This is a deliberate, documented tradeoff, not an oversight — no finding.
  - WhatsApp webhook: HMAC-SHA256 signature verified over the *raw* request body (not the re-serialized JSON, which would produce a different digest) before any processing; fails closed in production if the secret is unset, soft-warns only in dev.
  - Email webhooks (Resend/SendGrid): svix HMAC / provider-specific verification, same fail-closed-in-prod pattern.
  - Cron endpoints (`/api/cron`, `/api/v1/workers/cron`): timing-safe (`crypto.timingSafeEqual` over SHA-256 hashes) secret comparison, fails closed if the secret env var is unset.
  - No finding across any of the above — this is a well-hardened webhook layer.
- ✅ **No M-Pesa secrets found hardcoded or logged** — grepped for hardcoded credential patterns repo-wide, zero hits outside test fixtures; error responses reviewed in the prior `OPTIMIZATION_CLEANUP_AUDIT.md` pass specifically to strip raw error messages/stack traces from cron/worker/register responses (still in place, re-verified via reading the current file content, not just trusting the changelog).
- ✅ **Reconciliation race conditions** — the STK callback path uses `after()` (background execution post-ack) with the durable-audit-first pattern described above; the `mpesa_reconcile` job and the daily `gl_cash_reconciliation` job (from the accounting-audit series) provide an independent secondary check. No new race condition found in this pass beyond what's already tracked.
- **Low — National ID / PII exposure.** `vw_members_masked` (a view masking phone/email/national_id/date_of_birth/address by role) exists and `applyMemberMask`/`stripSecrets` are used in `members.service.ts` (this session's own password-hash-leak fix, see [[project-kitabu-yetu-production-incidents]], hardened this exact boundary). Spot-checked two routes that reference `national_id` directly (`import/template` — a CSV column-header template, not real data; the share-certificate PDF route — legitimately needs the member's real name, not `national_id`, for the certificate). No new PII leak found, but this pass did not exhaustively check all 66 services for a *second* unmasked `SELECT *`-style leak the way the members-service one was found — recommend that as a follow-up grep (`SELECT \*|RETURNING \*` across `lib/services` cross-referenced against tables with a `national_id`/`password_hash` column) rather than assuming clean.

## 2.4 Secrets & Config

- ✅ No hardcoded credentials found (grepped for `key|secret|password|passkey = "..."`-shaped literals ≥12 chars across `app`/`lib`, excluding test/example files — zero hits).
- ✅ `.env`/`.env.local` are git-ignored (confirmed via `git check-ignore`). No `.env.example` exists in the repo at all — `lib/env.ts`'s Zod schema is the actual single source of truth for what variables are required, which is arguably a *better* pattern than a stale example file (it fails at boot if a required var is missing, an example file can silently drift).
- ✅ `SUPABASE_SERVICE_ROLE_KEY` is declared in the env schema but is **only read by the dead `lib/supabase/server.ts`** (zero importers) — so today it's inert, not a live risk of accidental client-bundle exposure. Once that dead file is deleted (see `01-inventory.md` §5 recommendation), this variable and its two `NEXT_PUBLIC_SUPABASE_*` siblings become removable from the schema too.
- ✅ Service-role-equivalent access (`withAdminDb`, the BYPASSRLS pool) is never imported into any client component — confirmed it's a `lib/db` server-only module, and Next.js's `'use client'` boundary + the module never touching `next/headers`-free client code makes accidental bundling structurally unlikely; not independently bundle-analyzed this pass.

## 2.5 Input Validation

- ✅ **113 of 167 API routes use Zod** (`z.object`/`Schema.parse`) for request validation. The remaining 54 are predominantly GET-only list/read endpoints (no body to validate — query-string params are validated via their own smaller Zod schemas in most cases, e.g. `DividendQuerySchema`, `CreditScoreQuerySchema`, confirmed by direct reading in this session's Phase D table-pagination work) or webhook receivers (validated by signature, not a Zod body schema, which is correct — the payload shape comes from an external provider's contract, not a client we control). Not flagging the 54 as a gap without checking each one individually — recommend a follow-up pass specifically listing which of the 54 are genuinely unvalidated mutations (if any) vs. legitimately schema-free.
- ✅ **59 `z.enum(...)` usages found in `lib/validators/*.ts`** — status/type/role fields are validated against a fixed literal union at the API boundary, not accepted as free text and trusted to match a DB enum. Confirmed this pattern directly in several validators touched this session (`DividendQuerySchema`, `WhatsAppQuerySchema`, `CreditScoreQuerySchema`).
- ✅ **Damm check-digit validation exists as a DB-level `SECURITY DEFINER` function** (`damm_check_digit`/`damm_interim`/`damm_valid`) for ID-format integrity (membership numbers, group codes) — this is enforced at the database, not just the UI, so a direct API call with a malformed ID fails structurally rather than relying on client-side regex.
